# zensical ドキュメントの文章構成ルール

`docs/zensical/docs/` 配下の `.md` を新規作成・編集するときは、次の方針で書く。
目的は、**散文の羅列や、実施ログの垂れ流しにしない**こと。結論と要点が先に目に入り、詳細は必要なときに開く構成にする。

nav の同期は別ルール（`docs-zensical-nav-sync.md`）。このルールは**書き方**を扱う。

## 1. 散文は箇条書きにする

- 説明は、1 項目 1 文の箇条書きにする。複数文の段落で説明しない。
- 「理由」「条件」「結果」など、ラベルが付く内容は、`- 理由: …` の形にする。
- 手順は番号付きリスト（`1.`）にする。
- 同じ形の項目が 3 つ以上並ぶなら、表にする（例: 責任 / 特徴 / 依存、症状 / 原因）。
- 見出し直下に、何の説明も無く、コードだけを置かない。1 行でも、何を示すコードかを書く。

## 2. alert（`!!!`）と折り畳み（`???`）を使い分ける

!!! danger "GitHub 形式（`> [!IMPORTANT]`）は使わない"
    - Zensical 0.0.36 は、GitHub 形式の alert を描画しない。`[!IMPORTANT]` という文字が、そのまま出る。
    - 必ず、admonition 記法（`!!!` / `???`）を使う。
    - `important` という種別は無い。「重要」は `warning` か `danger` で表す。

| 種別 | 使いどころ |
|---|---|
| `!!! danger` | やってはいけないこと、禁止事項、事故につながる注意 |
| `!!! warning` | 必ず知っておくべき注意、前提、制限、順序の依存 |
| `!!! tip` | 知っていると楽になる補足、コツ、推奨のやり方 |
| `!!! note` | 補足説明、仕様の背景、用語の注記 |
| `!!! success` | 効果・利点・決め手 |
| `!!! question` | 未確認事項、未解決の論点 |
| `??? info` / `??? example` / `??? success` | 折り畳み。下の基準で使う |
| `??? failure` | 折り畳みで見せる NG 例 |

- 1 つの alert は、箇条書き 2〜5 項目に収める。長くなるなら分ける。
- alert を多用しない。1 画面に何個も並ぶなら、本当に目立たせるべきものに絞る。
- タイトルは、中身を一言で言い切る（例: 「`exit` と切断は別物」）。「注意」「補足」だけにしない。

## 3. 折り畳みにする基準

次のものは、`??? ...` で畳む。**結論・手順・注意は畳まない。**

- 10〜12 行以上の**コード例**（コマンドの 1〜2 行は畳まない）。
- **実機で確認した記録**、検証ログ、「やったこと」の経緯。
- 参照用の長い**表**（ログの種別一覧、フィールド定義など）。
- 事例、背景、補足の掘り下げ。
- 同じ形の項目の詳細（コマンドごとの使用例など）。

書き方:

````markdown
??? example "コード例（25 行）"
    ```dart
    // 本文は 4 スペースでインデントする
    ```
````

- タイトルは、開かなくても中身が分かるようにする（行数、対象、結論）。
- 折り畳みの中身は、すべて **4 スペース**インデントする（コード、表、リスト、入れ子の alert）。

## 4. 対比はタブにする

「望ましい結果 / よろしくない結果」「Before / After」のように、2 つを見比べさせるものは、タブにする（`pymdownx.tabbed` が有効）。

````markdown
=== "✅ 望ましい結果"

    ```
    出力例
    ```

=== "❌ よろしくない結果"

    ```
    出力例
    ```

    **問題点**: …
````

## 5. 記法の落とし穴（崩れの原因になる）

- **リストの直前には、空行を入れる。** 空行が無いと、リストにならず、1 段落に潰れる。
    - 特に `**トリガー条件:**` の直後の `- …` で起きやすい。
- **入れ子のリストは、4 スペース**でインデントする。2 スペースだと、階層が潰れる。
- admonition の中のリスト・表・コードは、4 スペース（入れ子の中は 8 スペース）でインデントする。
- 表の前後と、`!!!` / `???` / `===` の前後には、空行を入れる。
- HTML の `<details>` は使わない。`???` に統一する。

## 6. 書いたあとの確認

`docs/zensical/site/` は **git 管理されている生成物**。リポジトリ内で `zensical build` を実行すると、大量の差分が出る。
**ビルドは、作業コピーで行う。**

```bash
W=$(mktemp -d)
tar --exclude=./site --exclude=./.venv -cf - -C docs/zensical . | tar -xf - -C "$W"
(cd "$W" && uv run zensical build)
```

- 生成された `site/<ページ>/index.html` で、次の漏れが無いことを確認する。
    - `<p>` の中に、`**` や `|` や、行頭の `- ` / `1. ` がそのまま出ていない。
    - `!!!` / `???` / `===` の生マーカーが残っていない。
    - コードブロック内の `**` は、誤検出なので除く。
- 表・admonition・折り畳みの数が、元の内容から減っていないことを確認する。
- 画面で確認するときは `uv run zensical serve` を作業コピーで起動する。
    - ヘッドレス Chrome で撮る場合、日本語フォントが無いと豆腐になる。構造の確認だけなら、それでも足りる。
- 起動したサーバーは、確認が終わったら止める。

## 7. 内容は変えない

- 整形のための編集では、**事実・数値・手順・リンクを削らない**。
- 書き換えの前後で、情報が欠けていないか見比べる。
- 元の記述が古い・矛盾していると気づいたら、**黙って直さず、報告する**（例: 別ページと食い違う記述）。
