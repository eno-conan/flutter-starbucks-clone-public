ワークフロー・自律実行ガイド¶

Plan Mode の使い分け¶

  • 3ステップ以上 or アーキテクチャ判断を含むタスク → プランモードに入る
  • ユーザーから実装計画が与えられた場合 → 再分析せず直ちにコーディングを開始する。計画を読み、理解し、ファイル単位で実装を進める
  • 途中で詰まったら即 STOP → 再計画。強引に押し進めない
  • 検証フェーズにもプランモードを活用し、動作確認の手順を明確にする

Subagent 戦略¶

  • メインコンテキストウィンドウを守るためサブエージェントを積極的に活用する
  • 調査・探索・並列分析はサブエージェントにオフロードする
  • 複雑な問題には複数のサブエージェントで計算リソースを投入する
  • 1 サブエージェント = 1 タスク の原則で集中実行させる

自律バグ修正¶

  • バグ報告時は即修正。ユーザーへの手取り足取り確認は不要
  • ログ・エラー・失敗テストを起点に自律的に原因を特定して解決する
  • CI テストが落ちていたら指示なしでも修正に向かう

Elegance 要求（バランス重視）¶

  • 非自明な変更では「もっとエレガントな方法があるか？」と自問する
  • 解決策がハック的に感じたら：「今わかっていることを踏まえ、エレガントな解を実装する」と自らに問いかける
  • 単純・明白な修正ではこのステップをスキップ（過剰設計しない）

自己改善ループ¶

  • ユーザーから修正・指摘を受けたら tasks/lessons.md にパターンを記録する
  • 同じミスを防ぐルールを自分自身のために書く（ファイルが存在しない場合は初回時に作成する）
  • セッション開始時に関連プロジェクトの tasks/lessons.md が存在すれば確認する

ファイル形式: 

## [日付] パターン名
**状況**: どういう状況でミスが起きたか
**失敗**: 何をしてしまったか
**正しい対応**: どうすべきだったか
**ルール**: 今後このケースでは〇〇する

フィードバックループ設計¶

最大ラウンド数¶

同一問題に対する修正試行は 最大 3 ラウンド まで。

ラウンド 行動
1 問題を特定して修正を試みる
2 別アプローチで再試行
3 最後の試行。失敗したら即 STOP

Oscillation（循環）検出¶

以下のいずれかに該当したら「オシレーション」と判定して 即座に STOP：

  • 同一ファイルへの同じ修正を 2 回以上繰り返した
  • エラーメッセージが前回と同一のまま修正を繰り返している
  • A → B → A のような変更の往復が発生している

STOP 後の対応: 1. ユーザーに状況を報告（「X を 3 回試みましたが解決できませんでした」） 2. 根本原因の仮説を提示する 3. ユーザーの判断を仰ぐ。強引に押し進めない

Pivot（方針転換）判断¶

3 ラウンド以内に解決できない場合、以下の順で代替アプローチを検討する：

  1. テスト追加: 問題を再現するテストを書いて原因を絞り込む
  2. 仕様確認: Issue / CLAUDE.md / ルールファイルを再読して前提を確認する
  3. アーキテクチャ再定義: Plan Mode に入り直して設計から見直す

Generator-Evaluator 分離¶

実装後の品質確認には専任エージェントを呼び出す：

  • qa-agent: テスト実行・静的解析（コード修正権限なし）
  • security-agent: セキュリティ評価（コード修正権限なし）
  • riverpod-specialist: Riverpod 3.0 準拠チェック

完了検証チェック¶

タスクを完了とマークする前に必ず以下を実施する：

  • 動作証明を行う（テスト実行・ログ確認・動作デモ）
  • 主な変更と元の動作の差分を確認する
  • 「スタッフエンジニアならこのコードを承認するか？」と自問する
