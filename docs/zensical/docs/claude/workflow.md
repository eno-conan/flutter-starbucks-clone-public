# ワークフロー・自律実行ガイド

## Plan Mode の使い分け

- **3ステップ以上 or アーキテクチャ判断を含むタスク** → プランモードに入る
- **ユーザーから実装計画が与えられた場合** → 再分析せず直ちにコーディングを開始する。計画を読み、理解し、ファイル単位で実装を進める
- 途中で詰まったら即 STOP → 再計画。強引に押し進めない
- 検証フェーズにもプランモードを活用し、動作確認の手順を明確にする

## Subagent 戦略

- 既定は自分で直接やる。Claude 5 系は自分からサブエージェントを起動しやすいため、委譲には理由を要する（`model-routing.md` の「委譲しすぎない」）
- 委譲してよいのは次の 3 つ
    - 大量の出力を読む広い探索で、結論だけが要るとき（メインコンテキストを守る）
    - 互いに独立で、並列に進められる作業
    - 書いた本人以外の目が要るレビュー（後述の Generator-Evaluator 分離）
- 数回のツール呼び出しで済む調査や、自分の作業の再確認だけが目的の起動はしない
- 1 サブエージェント = 1 タスク。サブエージェントは会話の文脈を持たないので、プロンプトに目的・調査済みの事実・返してほしい形式（結論と根拠の `ファイル:行`）を書く
- 返答は参考情報として扱う。「〜は存在しない」「〜は問題ない」といった重要な主張は、自分で 1 回確認してから採用する

## 自律バグ修正

- バグ報告時は即修正。ユーザーへの手取り足取り確認は不要
- ログ・エラー・失敗テストを起点に自律的に原因を特定して解決する
- CI テストが落ちていたら指示なしでも修正に向かう
- ただし、元に戻せない・外部に影響する操作（削除・本番データ・権限変更・公開）は自律の対象外。事前にユーザーへ確認する。承認は別の文脈に持ち越さない

## Elegance 要求（バランス重視）

- 非自明な変更では「もっとエレガントな方法があるか？」と自問する
- 解決策がハック的に感じたら：「今わかっていることを踏まえ、エレガントな解を実装する」と自らに問いかける
- 単純・明白な修正ではこのステップをスキップ（過剰設計しない）

## 自己改善ループ

- ユーザーから修正・指摘を受けたら `tasks/lessons.md` にパターンを記録する
- 同じミスを防ぐルールを自分自身のために書く（ファイルが存在しない場合は初回時に作成する）
- セッション開始時に関連プロジェクトの `tasks/lessons.md` が存在すれば確認する
- 記録するのは今後も効く指摘（再発しうるミス）だけ。その場限りの指摘は残さない
- 古くなった・重複した教訓は、追記するついでに統合・削除する（読む量を増やさない）

ファイル形式:

```
## [日付] パターン名
**状況**: どういう状況でミスが起きたか
**失敗**: 何をしてしまったか
**正しい対応**: どうすべきだったか
**ルール**: 今後このケースでは〇〇する
```

## フィードバックループ設計

### 最大ラウンド数

!!! warning "同一問題に対する修正試行は、最大 3 ラウンドまで"
    3 ラウンド目で失敗したら、即 STOP する。

| ラウンド | 行動 |
|---|---|
| 1 | 問題を特定して修正を試みる |
| 2 | 別アプローチで再試行 |
| 3 | 最後の試行。失敗したら即 STOP |

### Oscillation（循環）検出

!!! danger "次のいずれかに該当したら、「オシレーション」と判定して即座に STOP"
    - 同一ファイルへの同じ修正を 2 回以上繰り返した
    - エラーメッセージが前回と同一のまま修正を繰り返している
    - A → B → A のような変更の往復が発生している

**STOP 後の対応**:

1. ユーザーに状況を報告（「X を 3 回試みましたが解決できませんでした」）
2. 根本原因の仮説を提示する
3. ユーザーの判断を仰ぐ。強引に押し進めない

### Pivot（方針転換）判断

3 ラウンド以内に解決できない場合、次の順で代替アプローチを検討する。

1. **テスト追加**: 問題を再現するテストを書いて原因を絞り込む
2. **仕様確認**: Issue / CLAUDE.md / ルールファイルを再読して前提を確認する
3. **アーキテクチャ再定義**: Plan Mode に入り直して設計から見直す

### Generator-Evaluator 分離

実装後の品質確認には、専任エージェントを呼び出す。

- **`code-reviewer`**: 差分の規約・設計レビュー（コード修正権限なし）
- **`qa-agent`**: テスト実行・静的解析（コード修正権限なし）
- **`security-agent`**: セキュリティ評価（コード修正権限なし）
- **`riverpod-specialist`**: Riverpod 3.0 準拠チェック

### Loop Engineering（`/dev-loop`）

- 上記のフィードバックループ（最大ラウンド数・オシレーション検知・Generator-Evaluator 分離）を、手順として実行可能にしたのが `/dev-loop` コマンド。

!!! warning "critical ティア（スキーマ・サービス層・RPC・認証・CI）専用"
    standard 以下は、通常作業 + Stop hook（`stop-gate.sh`）で足りる。

```
影響度判定 → 計画(Opus) → 実装(Sonnet/Haiku) → レビュー(Sonnet) → 判定 → 修正
```

- 影響度ティアは `bash .claude/scripts/impact-classify.sh <paths>` が決定論的に判定する
- 実装は `implementer`（Sonnet）、docs のみの定型作業は `docs-scribe`（Haiku）
- 計画は `plan-architect`（Opus）を 1 ループ 1 回まで
- 詳細: `.claude/rules/model-routing.md` / `.claude/skills/dev-loop/SKILL.md`

## 完了検証チェック

タスクを完了とマークする前に、必ず次を実施する。

- 動作証明を行う（テスト実行・ログ確認・動作デモ）。変更に最も近い検証から実行する
- バグ修正は、先に失敗を再現し、修正後に同じ手順で通ることを示す
- 主な変更と元の動作の差分を確認する
- 実行できなかった検証は「未実施」と明記する。失敗はそのまま報告し、テストのスキップ・弱体化で通さない
- 自分の差分を読み直し、「スタッフエンジニアならこのコードを承認するか？」と自問する
