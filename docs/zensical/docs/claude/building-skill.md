# Claude スキル構築ガイド

- リポジトリ最適化のための、要約レポート。
- シニア・テクニカル・アーキテクトの視点で、Claude に特定のドメイン知識やワークフローを学習させ、一貫した出力をエンジニアリングするための「スキル（Skill）」の、設計・実装・運用をまとめたもの。
- 開発者が即座に実装へ移せるよう、厳格な技術仕様とベストプラクティスを構造化して示す。

参照元:

- <https://claude.com/blog/complete-guide-to-building-skills-for-claude>
- <https://github.com/shanraisshan/claude-code-best-practice?tab=readme-ov-file>

## 1. スキルの定義と基本構成

### スキルの概念

- 「スキル」とは、Claude に特定のタスクやプロセスを教えるための、パッケージ化された指示セット。
- 単なるプロンプトの集合体ではない。次のものをカプセル化した、再利用可能なモジュールとして機能する。
    - ドメイン知識
    - 実行コード
    - 参照ドキュメント

### MCP とスキルの関係: キッチンとレシピの比喩

| | 比喩 | 役割 |
|---|---|---|
| **MCP**（Connectivity） | プロフェッショナルな「キッチン」 | ツール、材料（データ）、設備（接続性）へのアクセスを提供する |
| **スキル**（Knowledge） | 「レシピ」 | 価値あるものを生み出すための、ツールの使い方の段階的な指示とベストプラクティスを提供する |

### 基本フォルダ構造

スキルは、次の標準化されたフォルダ構造を持つ必要がある。

| 項目 | 必須 | 内容 |
|---|---|---|
| `SKILL.md` | 必須 | メインの指示書。YAML フロントマターによるメタデータと、Markdown 形式の指示を記述する |
| `scripts/` | 任意 | 実行可能コード（Python, Bash など）。複雑な検証など、決定論的な処理が必要な場合に使う |
| `references/` | 任意 | API ガイドや仕様書など、必要に応じてロードされるドキュメント |
| `assets/` | 任意 | 出力で使うテンプレート、アイコン、フォントなどのアセット |

## 2. コア設計原則

### 段階的開示（Progressive Disclosure）

- トークン使用量を最小限に抑えつつ、専門性を発揮するため、次の 3 レベルのシステムを採用している。

| レベル | 対象 | ロードされるタイミング |
|---|---|---|
| 1 | YAML フロントマター | 常にシステムプロンプトにロードされる。Claude がスキルの使用要否を判断するための、最小限の情報を提供する |
| 2 | `SKILL.md` 本文 | タスクに関連があると判断されたときのみ |
| 3 | リンクされたファイル | 必要に応じて、Claude が探索・参照する追加リソース |

### 構成可能性（Composability）

- Claude は、複数のスキルを同時にロードできる。
- 各スキルは、他のスキルの存在を前提とせず、独立して機能しつつ共存できるよう設計しなければならない。

### ポータビリティ（Portability）

- 「Agent Skills」は、オープン標準として公開されている。
- 一度作成したスキルは、Claude.ai、Claude Code、API の各環境で、修正なしに動作する。

## 3. 技術的要件と命名規則

!!! danger "クリティカル・ルール"
    リポジトリが Claude に正しく認識されるためには、次のルールを厳守する必要がある。

### ファイル・フォルダ命名の制約

- **`SKILL.md`**: 綴りと大文字・小文字を完全に一致させる（`skill.md` などは認識されない）。
- **フォルダ名**: kebab-case のみ（例: `project-setup-skill`）。スペース、アンダースコア、大文字は禁止。
- **`README.md` の禁止**: スキルフォルダ内に `README.md` を置いてはならない。すべてのドキュメントは、`SKILL.md` か `references/` に集約する。

### YAML フロントマターの詳細スキーマ

- `SKILL.md` の冒頭には、次のフィールドを含む YAML が必要。

```yaml
---
name: your-skill-name # フォルダ名と一致させる
description: |
  [何をするか] + [いつ使用するか] を記述。
  ユーザーが発する可能性のある具体的なフレーズや、関連するファイル形式を含める。
license: MIT # 公開する場合に推奨
compatibility: |
  環境要件（製品、システムパッケージ、ネットワークアクセス等）を記述。
metadata:
  author: ProjectName
  version: 1.0.0
  mcp-server: server-name
---
```

- **文字数制限**: `description` は 1024 文字以内、`compatibility` は 500 文字以内。

!!! warning "セキュリティ禁止事項"
    - フロントマター内で、XML タグ（`< >`）を使わない。
    - スキル名に、「claude」「anthropic」を使わない（予約語）。

## 4. スキルのカテゴリーと設計パターン

開発するスキルが、次のどのカテゴリーに該当するかを特定すると、設計の方向性が定まる。

1. **ドキュメント・アセット作成**: テンプレートやスタイルガイドを埋め込み、高品質な成果物を一貫して生成する。
2. **ワークフロー自動化**: 複数のステップを持つプロセスを定義し、バリデーションゲートを設けて進行させる。
3. **MCP 拡張**: MCP が提供する生のツールアクセスに対し、ドメイン知識に基づいた実行ガイダンスを付加する。

## 5. 効果的な指示（Instructions）の作成

### 推奨 Markdown 構造

- `SKILL.md` の本文では、次のヘッダー構造を使い、視認性と指示の強制力を高める。

| ヘッダー | 内容 |
|---|---|
| `# スキル名` | スキルの名前 |
| `## CRITICAL` または `## IMPORTANT` | 遵守すべき最重要ルール（バリデーション、制限事項） |
| `# Instructions` | ステップごとの具体的な手順 |
| `# Examples` | ユーザーの入力、アクション、結果の具体例 |
| `# Troubleshooting` | 一般的なエラーと解決策 |

### アーキテクトによるベストプラクティス

- **決定論的処理の分離**
    - 言語モデルによる解釈は、非決定的。
    - 複雑な検証やデータ変換は、`SKILL.md` の指示に頼らず、`scripts/` 内のコードに実行させる。
- **段階的開示の徹底**
    - 膨大な API リファレンスなどは、`references/` に分離する。
    - 必要なときだけ、リンクから参照させる。
- **「怠慢」対策の適正化**
    - 「品質を優先せよ」といった、モデルの怠慢を防ぐ励ましは、`SKILL.md` に含めるより、ユーザープロンプトに動的に追加するほうが効果的。
- **`skill-creator` の活用**
    - `skill-creator` スキルは、スキルの生成、YAML の検証、トリガーの最適化を行う主要ツール。
    - 開発の起点として活用を推奨する。

## 6. テスト、改善、および成功指標

- スキルを、「ベースライン（スキルなしの状態）」と比較して評価する。

### 成功指標の定義

| カテゴリ | 指標 | 評価基準 |
|---|---|---|
| 定量的指標 | トリガー率 | 関連クエリに対して、90% 以上自動ロードされること |
| 定量的指標 | 効率性 | スキルなしと比較した際の、ツール呼び出し回数および総消費トークン量の削減 |
| 定量的指標 | エラー率 | ワークフローあたりの、API エラー / リトライ回数の減少 |
| 定性的指標 | 自律性 | ユーザーによる、次ステップの指示や修正プロンプトが不要であること |
| 定性的指標 | 一貫性 | 複数回の実行において、出力の構造と品質が安定していること |
| 定性的指標 | 初見成功率 | 新規ユーザーが、最小限のガイダンスでタスクを完了できること |

### 継続的改善（トリガーの最適化）

- **アンダートリガー（反応が悪い）**: `description` に、技術用語、具体的なユーザーフレーズ、関連ファイル拡張子を追加する。
- **オーバートリガー（過剰反応）**: ネガティブトリガーを `description` に明記し、スコープを絞り込む。
    - 例: 「Do NOT use for simple data exploration」。

## 7. プリフライト・チェックリスト

デプロイ前に、次の項目を最終確認する。

- [ ] フォルダ名が kebab-case であり、スペースや大文字を含まないか。
- [ ] `SKILL.md` は、正確な綴りと大文字表記になっているか。
- [ ] YAML フロントマターが、`---` で正しく囲まれているか。
- [ ] `description` に、「何をするか」と「いつ使用するか（トリガー）」の両方が含まれているか。
- [ ] フロントマター内に、XML タグ（`< >`）が含まれていないか。
- [ ] フォルダ内に、`README.md` が混入していないか。
- [ ] 重要な手順に、`## CRITICAL` などのヘッダーを使っているか。
- [ ] 複雑な検証には、`scripts/` を活用しているか。
- [ ] ベースラインと比較して、トークン消費量やメッセージ往復回数が改善されているか。
