# 設計書テンプレート

- 新しい設計書は、このテンプレートをコピーして `NNNN-<title>.md` で作る。
- 書き方の原則と、ワンページャー / ツーページャーとの使い分けは [設計書の書き方と運用](index.md) を参照。
- 該当しない節は削除せず、「該当なし（理由）」と 1 行で書く。観点の見落としと、意図的な省略を区別するため。

!!! tip "短い変更向けの最小構成"
    - ワンページャー（Issue / PR の説明）では、次の 5 項目だけ書く。
    - 1. 背景と問題 / 2. ゴールと非ゴール / 3. 変更内容 / 4. 検証方法 / 5. 影響範囲と戻し方

## テンプレート本体

````markdown
# NNNN: <変更内容を一言で>

| 項目 | 内容 |
|---|---|
| ステータス | Draft / In Review / Accepted / Implemented / Rejected / Superseded |
| 作成者 | |
| レビュアー | |
| 作成日 / 最終更新日 | YYYY-MM-DD / YYYY-MM-DD |
| 関連 Issue / PR | |
| 影響度ティア | critical / standard（`bash .claude/scripts/impact-classify.sh <paths>` の結果） |
| 置き換え / 置き換えられた設計書 | なし |

## 要約（TL;DR）

- 何を変えるか（1 文）。
- なぜ変えるか（1 文）。
- 採用する方式と、決め手（1〜2 文）。

## 1. 背景

- 現状: いまどう動いているか。再現手順・エラー・ユーザーの体験を先に示す。
- 問題: 何が困っているか。表にする（# / 問題 / 詳細）。
- 解決策は、ここには書かない。

## 2. ゴールと非ゴール

**ゴール:**

- この設計で達成すること。検証できる形で書く。

**非ゴール:**

- この設計では、あえてやらないこと。
- 「やらない理由」も 1 行で添える。

## 3. 設計

### 3.1 全体像

- 構成図、またはレイヤーごとの責務の表。

### 3.2 処理の流れ（シーケンス図）

- 正常系を 1 枚、異常系・フォールバックを別の 1 枚で描く。
- 登場人物は 6 つ以内。名前は実装と同じにする。

### 3.3 データ・インターフェース

- テーブル、RPC、モデル、公開する API の変更。
- スキーマ変更は、移行 SQL の方針と、既存データの扱いも書く。

### 3.4 変更するファイル

| ファイル | 区分（新規 / 変更 / 削除） | 内容 |
|---|---|---|

## 4. 検討した代替案

| 案 | 長所 | 短所 | 採用しなかった理由 |
|---|---|---|---|

## 5. 横断的関心事

| 観点 | 検討内容 |
|---|---|
| セキュリティ | 認証・認可、RLS、秘密情報の扱い（`security-agent` の観点） |
| プライバシー | 取得・保存する個人情報、保持期間 |
| 互換性 | 既存ユーザー・古いアプリバージョンへの影響 |
| 性能 | 想定する負荷、N+1、インデックス |
| 可観測性 | ログ、メトリクス。機密情報を出さないこと |
| テスト | 単体 / Widget / 統合の方針と、実機で確認する項目 |
| アクセシビリティ・多言語 | 該当する場合のみ |

## 6. 移行とロールアウト

- 実装の順序（フェーズ）と、各フェーズの完了条件。
- 順序の依存（例: 先にアプリ、後にマイグレーション）。
- 失敗したときの戻し方。

## 7. 未解決の論点

| # | 論点 | 選択肢 | 推奨 | 決める人 |
|---|---|---|---|---|

## 8. 決定事項と実装時の差分

- 合意した内容と日付。
- 実装中に設計から変えた点と、その理由。

## 9. 参考

- 参照した公式ドキュメント・ソース・Issue。
````

## 各節を書くときの観点

| 節 | 書くときの問い |
|---|---|
| 背景 | 設計書を読まない人にも、問題が伝わるか。解決策が混ざっていないか |
| ゴールと非ゴール | 完了したかを、第三者が判定できるか。非ゴールは、議論の余地があるものを選んだか |
| 設計 | 実装者が迷わないか。シーケンス図とコードの名前が一致しているか |
| 代替案 | 「やらない案」が藁人形になっていないか。採用案の短所も書いたか |
| 横断的関心事 | 全観点を見出しで確認したか。省略するなら、理由を書いたか |
| 移行とロールアウト | 途中で止めても壊れないか。戻せるか |
| 未解決の論点 | 具体的な選択肢と推奨を示し、決める人を決めたか |

## シーケンス図の雛形

- 認証・通知のように、ユーザー・画面・サービス・外部サービスが関わる流れの雛形。
- 異常系は、`alt` / `opt` で同じ図に書くか、別の図にする。

??? example "正常系と異常系を 1 枚にまとめる雛形（22 行）"
    ```mermaid
    sequenceDiagram
        participant U as ユーザー
        participant UI as XxxScreen
        participant S as XxxService
        participant SB as Supabase

        U->>UI: 操作
        UI->>S: execute()
        S->>SB: RPC 呼び出し
        alt 成功
            SB-->>S: 結果
            S-->>UI: 成功
            UI-->>U: 完了表示
        else 業務エラー
            SB-->>S: エラー
            S-->>UI: 失敗（種別つき）
            UI-->>U: メッセージ表示
        end
        opt ユーザーキャンセル
            U-->>UI: キャンセル
            UI-->>U: 何も表示せず元の画面へ
        end
    ```
