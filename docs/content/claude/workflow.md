# ワークフロー・自律実行ガイド

## Plan Mode の使い分け

- **3ステップ以上 or アーキテクチャ判断を含むタスク** → プランモードに入る
- **ユーザーから実装計画が与えられた場合** → 再分析せず直ちにコーディングを開始する。計画を読み、理解し、ファイル単位で実装を進める
- 途中で詰まったら即 STOP → 再計画。強引に押し進めない
- 検証フェーズにもプランモードを活用し、動作確認の手順を明確にする

## Subagent 戦略

- 既定は自分で直接やる。Claude 5 系は自分からサブエージェントを起動しやすいため、委譲には理由を要する（`model-routing.md` の「委譲しすぎない」）
- 委譲してよいのは次の 3 つ
    - 大量の出力を読む広い探索で、結論だけが要るとき（メインコンテキストを守る）
    - 互いに独立で、並列に進められる作業
    - 書いた本人以外の目が要るレビュー（後述の Generator-Evaluator 分離）
- 数回のツール呼び出しで済む調査や、自分の作業の再確認だけが目的の起動はしない
- 1 サブエージェント = 1 タスク。サブエージェントは会話の文脈を持たないので、プロンプトに目的・調査済みの事実・返してほしい形式（結論と根拠の `ファイル:行`）を書く
- 返答は参考情報として扱う。「〜は存在しない」「〜は問題ない」といった重要な主張は、自分で 1 回確認してから採用する

## 自律バグ修正

- バグ報告時は即修正。ユーザーへの手取り足取り確認は不要
- ログ・エラー・失敗テストを起点に自律的に原因を特定して解決する
- CI テストが落ちていたら指示なしでも修正に向かう
- ただし、元に戻せない・外部に影響する操作（削除・本番データ・権限変更・公開）は自律の対象外。事前にユーザーへ確認する。承認は別の文脈に持ち越さない

## Elegance 要求（バランス重視）

- 非自明な変更では「もっとエレガントな方法があるか？」と自問する
- 解決策がハック的に感じたら：「今わかっていることを踏まえ、エレガントな解を実装する」と自らに問いかける
- 単純・明白な修正ではこのステップをスキップ（過剰設計しない）

## 自己改善ループ

- ユーザーから修正・指摘を受けたら `tasks/lessons.md` にパターンを記録する
- 同じミスを防ぐルールを自分自身のために書く（ファイルが存在しない場合は初回時に作成する）
- セッション開始時に関連プロジェクトの `tasks/lessons.md` が存在すれば確認する
- 記録するのは今後も効く指摘（再発しうるミス）だけ。その場限りの指摘は残さない
- 古くなった・重複した教訓は、追記するついでに統合・削除する（読む量を増やさない）

ファイル形式:

```
## [日付] パターン名
**状況**: どういう状況でミスが起きたか
**失敗**: 何をしてしまったか
**正しい対応**: どうすべきだったか
**ルール**: 今後このケースでは〇〇する
```

## フィードバックループ設計

### 最大ラウンド数

!!! warning "同一問題に対する修正試行は、最大 3 ラウンドまで"
    3 ラウンド目で失敗したら、即 STOP する。

| ラウンド | 行動 |
|---|---|
| 1 | 問題を特定して修正を試みる |
| 2 | 別アプローチで再試行 |
| 3 | 最後の試行。失敗したら即 STOP |

### Oscillation（循環）検出

!!! danger "次のいずれかに該当したら、「オシレーション」と判定して即座に STOP"
    - 同一ファイルへの同じ修正を 2 回以上繰り返した
    - エラーメッセージが前回と同一のまま修正を繰り返している
    - A → B → A のような変更の往復が発生している

**STOP 後の対応**:

1. ユーザーに状況を報告（「X を 3 回試みましたが解決できませんでした」）
2. 根本原因の仮説を提示する
3. ユーザーの判断を仰ぐ。強引に押し進めない

### Pivot（方針転換）判断

3 ラウンド以内に解決できない場合、次の順で代替アプローチを検討する。

1. **テスト追加**: 問題を再現するテストを書いて原因を絞り込む
2. **仕様確認**: Issue / CLAUDE.md / ルールファイルを再読して前提を確認する
3. **アーキテクチャ再定義**: Plan Mode に入り直して設計から見直す

### Generator-Evaluator 分離

実装後の品質確認には、専任エージェントを呼び出す。

- **`code-reviewer`**: 差分の規約・設計レビュー（コード修正権限なし）
- **`qa-agent`**: テスト実行・静的解析（コード修正権限なし）
- **`security-agent`**: セキュリティ評価（コード修正権限なし）
- **`riverpod-specialist`**: Riverpod 3.0 準拠チェック

### Loop Engineering（`/dev-loop`）

- 上記のフィードバックループ（最大ラウンド数・オシレーション検知・Generator-Evaluator 分離）を、手順として実行可能にしたのが `/dev-loop` コマンド。

!!! warning "critical ティア（スキーマ・サービス層・RPC・認証・CI）専用"
    standard 以下は、通常作業 + Stop hook（`stop-gate.sh`）で足りる。

```
影響度判定 → 計画(Opus) → 実装(Sonnet/Haiku) → レビュー(Sonnet) → 判定 → 修正
```

- 影響度ティアは `bash .claude/scripts/impact-classify.sh <paths>` が決定論的に判定する
- 実装は `implementer`（Sonnet）、docs のみの定型作業は `docs-scribe`（Haiku）
- 計画は `plan-architect`（Opus）を 1 ループ 1 回まで
- 詳細: `.claude/rules/model-routing.md` / `.claude/skills/dev-loop/SKILL.md`

## Stacked PR（積み上げ PR）

- 目的: 大きな変更を、レビューしやすい小さな PR の積み重ねに分ける
- 提供状況: 2026-10-06 に GA。github.com の全プランで利用できる（Free を含むと読み取れるが、changelog に「Free」の明記はない）
- 準備: `gh extension install github/gh-stack`（`gh` 本体の更新はパッケージマネージャで行う）
- 仕組み: 各 PR は 1 つ下の層を base にし、その層の差分だけをレビューする
- マージ: 下の層だけをマージできる。その場合、上の PR は自動でリベースされ、base も付け替わる

!!! note "このリポジトリの CI は、base が `main` 以外の PR でも動く"
    - `pull_request:` を使うワークフローに `branches:` の絞り込みは無い
    - `push:` は `main` に限定されているため、スタックの途中の層は PR 側のトリガーだけで検証される
    - `paths:` の判定が、PR の base に対する差分で行われるかは、試験運用で確認する

!!! question "未確認事項"
    - スタックの全ブランチを同一リポジトリに置く必要がある（フォーク越しは非対応）という情報は二次情報で、公式ドキュメントでは未確認
    - 通常の PR を base チェーンで作った場合に、スタックとして認識されるか
    - マージキューと Auto-merge for stacks は段階的に展開中

- 参照: [Issue #1158](https://github.com/eno-conan/flutter-starbucks-clone/issues/1158) / [GA の changelog](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available)

## 完了検証チェック

タスクを完了とマークする前に、必ず次を実施する。

- 動作証明を行う（テスト実行・ログ確認・動作デモ）。変更に最も近い検証から実行する
- バグ修正は、先に失敗を再現し、修正後に同じ手順で通ることを示す
- 主な変更と元の動作の差分を確認する
- 実行できなかった検証は「未実施」と明記する。失敗はそのまま報告し、テストのスキップ・弱体化で通さない
- 自分の差分を読み直し、「スタッフエンジニアならこのコードを承認するか？」と自問する

## PR のマージ前の確認

- 目的: 並行する PR のあいだで起きる食い違い（例: マイグレーションの版の重複。#1192）を、マージの前に拾う。
- 背景: このリポジトリは、非公開の Free プランで、ブランチ保護（「最新の main であることを必須にする」）を使えない。CI のあとに main が進んでも、GitHub はマージを止めない。

### マージの直前に行うこと

1. `git fetch origin main` のあと、PR のブランチが main の先頭を含んでいるかを確認する（`git merge-base --is-ancestor origin/main <PR のブランチ>`。終了コード 0 なら含んでいる）。
    - PR の `base.sha` は比べない。`base.sha` は、PR を作った時点の main であり、ブランチが含んでいる main ではない。ブランチが古くても、一致して見える（実例: #1203。ブランチが古い main から作られていたのに、`base.sha` は PR 作成時の main だった）。
2. 含んでいるなら、そのままマージしてよい（CI・競合・レビューコメントの確認は、これまでどおり）。
3. 含んでいない（main が進んでいる）なら、次を行う。
    1. main を、PR のブランチへ取り込む（`git merge origin/main`）。競合は解く。
    2. push して、CI を回し直す。
    3. 結果が出てから、マージする。
4. マイグレーションを含む PR は、取り込んだあとに、`bash scripts/check-migration-versions.sh` が成功することも確認する。

### 例外

- ユーザーが「今すぐマージ」と指示し、main の進みが、PR と無関係な変更（docs のみなど）に限られるときは、進んでいることを報告したうえで、ユーザーの判断を仰ぐ。判断を待たずに、取り込みと再実行を省かない。
- 自分の PR で、他人のブランチは書き換えない。取り込みは、マージコミット（履歴を書き換えない形）で行う。

## Issue の完了処理

- 目的: 完了した Issue に、未チェックの項目や古い「現状」が残り、進捗を誤読されるのを防ぐ。
- 対象: 自分の PR（`Closes #N`）で閉じた Issue と、その親 Issue だけ。
- タイミング: PR がマージされ、Issue が閉じたあと。

### 確認なしで行うこと

1. 閉じた Issue 本文の `- [ ]` のうち、完了した項目だけを `- [x]` にする。
    - 未実施・対象外の項目は、チェックしない。理由を項目の末尾に 1 行添える。
    - 本文のほかの部分は、書き換えない。
2. サブ Issue なら、親 Issue の進捗（`sub_issues_summary`）が増えたことを確認する。
    - 進捗は GitHub が自動で更新する。親に手書きのチェックリストを新設・修正しない。
3. 親 Issue 本文に手書きの「現状」があり、今回の完了で古くなる場合だけ、その行を更新する。
4. 完了条件に後続作業が書かれていれば、実施済みかを確認する。未実施なら報告する。
    - 例: 「完了後、設計書 0001 の 3.8 に、自動化できた項目を記載する」。
5. 更新した Issue と項目を、報告に書く。

### 確認が要ること

| 操作 | 理由 |
|---|---|
| Issue のクローズ・再オープン（親を含む） | 完了の判断は開発者が行う |
| 新規 Issue の起票（「報告にとどめたもの」の Issue 化など） | 管理対象の件数が変わる |
| コメントの投稿 | 通知が飛ぶ |
| ラベル・担当者の変更 | 運用の取り決めを変えうる |

!!! tip "全サブ Issue が完了したとき"
    - 「親 Issue をクローズできる」と報告するだけにする。クローズは開発者が判断する。
